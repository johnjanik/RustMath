## 2. Blocker

### B1. `two_torsion_analysis` (and so `two_torsion_frobenius_order`) can exhaust memory inside its documented limits

`analyse` (`two_torsion.rs:463`) computes `fp.power_sums(2 * g * N_max)` at full precision and
keeps all of them; `s_n` has about `n log2(q) / 2` bits, so the memory grows like
`(g N_max)^2 log2(q)`. The only limit is `N_max <= MAX_BASE_CHANGE_DEGREE = 4096`.

Reproduction (`review1/probe/probe.rs`, case `nmax`): genus 12, `P` with the functional equation
and `P mod 2 = (x+1)^2 f f*`, `f = x^11 + x^2 + 1` (order 2047), so `N_max = 4094`:

- `q = 3`: 5.7 s and 558 MB resident;
- `q = 10^9 + 7`, under a 3 GB address-space cap: `memory allocation of 96616 bytes failed`,
  the process aborts after 72 s at 2.85 GB (about 10 GB would be needed).

Before this change `two_torsion_frobenius_order` on this `P` returned
`Unresolved { 2047, 4094 }` at once. An allocation failure aborts the process; it cannot be
caught, and the doc of both functions promises only two panics (a factor of degree above 62, an
order above `u64`). The M23 rows are not affected (genus 4, `N_max <= 30`), but the function is
public and its old cost was trivial for every genus with factors of degree at most 62. Genus 10
to 12 curves over large fields with such a `P mod 2` need 0.4 to 10 GB.

Required change: bound the cost of the bounds. Either (a) compute only `min(v_2, 2g + 1)` of
`P^(k)(+-1)`, which is all the rule uses (`r_k <= 2g`), for instance as the valuation of
`det(C^k -+ I)` over `Z/2^(2g+1)` with the companion matrix `C` raised by binary powering; a
vacuous bound and a zero group order then have the same effect, so no exact zero test is
needed; or (b) refuse with `TooLarge` when an estimate of the work (`2g N_max` power sums of up
to `g N_max log2 q` bits) exceeds a stated budget, so that `two_torsion_frobenius_order` falls
back to `mod2_bound`, and document the cost. Add a regression test with this `P` at
`q = 10^9 + 7` that returns quickly with bounded memory, and keep `c5_bounds_equal_pari` green
(with (a), the reported `v2` would be truncated at `2g + 1`; say so in the JSON or keep the exact
value where it is cheap).

## 3. Minor items

**m1. Undocumented panic for multiplicities 417 to 1000** (`two_torsion.rs:422-429`). The count
calls `partition_count`, which returns `usize` and panics when `p(n)` exceeds it (from about
`n = 416`); the saturation starts only above 1000. `(T^2+5)^210` (`P mod 2 = (x+1)^420`): both
`two_torsion_analysis` and `two_torsion_frobenius_order` panic with
`partition_count: p(n) exceeds usize::MAX`; `(T^2+5)^208` gives `TooManyCandidates` and
`(T^2+5)^501` saturates. Required: saturate before `partition_count` can overflow (any
multiplicity with `p(e) > MAX_CANDIDATES`, i.e. `e >= 61`, already decides the error; or use
`number_of_partitions`), and add the case to `too_many_candidates_and_errors`.

**m2. The cost of `lagrangian_types` near `MAX_LR_SIZE = 16` is not stated.** With the debug
rlibs: `(x+1)^8` 0.43 s, `(x+1)^12` 51 s, `(x+1)^16` not finished after 20 min (stopped;
`review1/probe/lag8.txt`, 33 MB resident). The limit suggests multiplicity 16 is supported; the
doc says nothing about the time. Required:
document the cost, or lower `MAX_LR_SIZE` to what runs in seconds, or both. The M23 layer
(multiplicity at most 8) is not affected.

**m3. The analysis is computed three times per row.** `checks_of_counts` calls
`two_torsion_frobenius_order` (field `two_torsion`), and `jac2_of` calls
`two_torsion_analysis` and then `two_torsion_frobenius_order` again. Cheap for genus 4; with B1
it multiplies the cost. Use `analysis.order()` when the analysis is `Ok`.

**m4. A dangling path in the header of `two_torsion.rs:13`**: "The proofs are in the design C57
(`docs/workstreams/m23_golay/c57/`)". That directory does not exist; the design is only in the
scratchpad. The Docs phase plans the copy (report 10.2); it must happen in the same PR, or the
header must point to where the proofs will be.

**m5. Refused L rows and the owner's `reason`.** C-7 promises the owner's keys. On the refused L
rows the key `reason` has RustMath's text, which differs from `zeta_L.json` at (5, 3)
("the degree in V drops mod p"), (23, 5) and (23, 15) ("the characteristic divides the degree in
V"); RustMath writes "model degenerate at this prime: the discriminant vanishes identically mod
p" for all four. The counted L rows also carry `certificate.certified`, which the owner's L rows
lack (a superset, harmless). This text comes from F-9, not this unit, but a script that compares
the two files will see it. Required: say it in the report's Section 3 for the owner, and
consider whether "the discriminant vanishes identically" is the accurate reason where the owner
sees a drop of the V-degree (out of scope here if it needs F-9 code).

**m6. The text output does not name H_W.** The W columns print `(Decided)` with no mention of
the trusted hypothesis; the JSON records it in every row (`trusted_hypotheses`,
`W_hypothesis`). REQUESTS Section 4 asks that trusted inputs be recorded in every result. One
header line in the text output (`# W columns assume H_W: ...`) would do.

**m7. Wording of the class status.** `class 1 7 (8 letters), 1 7^2 (15 points) (Decided; Q or
Q^rev not decided)`: when `Q != Q^rev` the class of `GL_4(2)` is not decided (two classes of
order 7, or of order 15), only its cycle types are. The JSON key `W_cycle_types_status` is
precise; the text could say `cycle types ... (Decided; the class depends on Q or Q^rev)`.
