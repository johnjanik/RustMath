## Blocker

### B1. S2: §1.7 dismisses public counting functions that have the same overflow class

§1.7 says that besides the sites of §1.6 the remaining `as u32` casts "take small sizes from
enumerations; they cannot reach 2^32 without first enumerating 2^32 objects", and step 11 of the plan
writes that into HANDOFF. That is false for these public closed-form counts (reproduced with
`review1/sib.rs`, `sib2.rs`, `sib3.rs` against the HEAD release rlib):

| function | defect | HEAD output | reference |
|---|---|---|---|
| `integer_vectors::count_integer_vectors_with_sum(length, sum)` (`integer_vectors.rs:239-251`, re-exported `lib.rs:256`) | the same body as `stars_and_bars`: `(sum + length - 1) as u32` truncates and `.unwrap_or(0)` turns an overflow into 0 | (3, 2^32) -> 1; (1000, 1000) -> 0 | gp `binomial(2^32+2, 2)` = 9223372043297226753; C(1999, 999) has 1994 bits |
| `six_vertex_model::partition_function(n: usize)` (`six_vertex_model.rs:528-535`) | `count_dwbc_configurations(n as u32)` | (2^32 + 3) -> 7 = A(3), at once | no value (it is A(2^32+3)); the honest answer is a panic or a wide argument |
| `parking_function::count_parking_functions(n)` (`parking_function.rs:311-316`) | `(n + 1).pow((n - 1) as u32)` in usize | 17 -> 10759066654336942080 (release; debug panics "attempt to multiply with overflow") | gp `18^16` = 121439531096594251776 |
| `count_non_decreasing_parking_functions(n)` (`parking_function.rs:321`, private `catalan_number` usize DP) | usize overflow | 37 -> 9057316177202639132 | `catalan(37)` = gp `binomial(74,37)/38` = 45950804324621742364 |
| `TupleIterator::count(&self)` (`tuple.rs:252-257`) | `saturating_pow`: silently returns usize::MAX | (2, 64) -> 18446744073709551615; (3, 41) -> the same | gp `2^64`, `3^41` = 36472996377170786403 |

The first two are u32 truncations inside rustmath-combinatorics, so they are inside S2 as worded; the
first is a facade identical to the `stars_and_bars` facade that §1.6 fixes. The usize ones are the
class of `partition_count` (`partitions.rs:1261`, also named in S2). None has a caller outside its
file (grep of the workspace).

Required change: add these to §1.6 with the same treatment and tests, and correct §1.7.
- `count_integer_vectors_with_sum`: exactly the `stars_and_bars` fix (Integer arithmetic on u64
  values, `to_usize()`, documented panic "exceeds usize::MAX"); tests (3, 2^32) = 9223372043297226753
  (64-bit only) and `#[should_panic]` on (1000, 1000).
- `six_vertex_model::partition_function`: `u32::try_from(n)` with a documented panic (or widen
  `asm_count`); test that (2^32 + 3) panics instead of returning 7 (64-bit only).
- `count_parking_functions`: `checked_pow` (and `u32::try_from(n - 1)`) with a documented panic;
  test 16 -> 17^15 = 2862423051509815793 (gp) and `#[should_panic]` at 17.
- `count_non_decreasing_parking_functions`: `crate::catalan(u32::try_from(n))` then `to_usize()` with a
  documented panic (drops the duplicate usize Catalan); test 36 -> 11959798385860453492 (gp
  `binomial(72,36)/37`) and `#[should_panic]` at 37.
- `TupleIterator::count`: `checked_pow` with a documented panic (or return `Option<usize>`; no caller);
  test (2, 63) = 2^63 and a panic at (2, 64).
- §1.7 then lists only casts that really are bounded by an enumeration (expnums, species, tamari test,
  path_tableaux test, `fully_packed_loop.rs:516` inside an O(n) loop of factorials) and the ranking
  module; the HANDOFF line says exactly that.

## Minor

### m1. HRR: the termination claim is false above about 8.4·10^16 (MPFR exponent range)
rug uses MPFR's default exponent range, emax = 2^30 - 1 (`review1/expr.rs`: `rug::float::exp_max()` =
1073741823; cosh(7.5e8) at 64 bits is +inf). U(C) with C = (pi/6) sqrt(24n - 1) overflows once
C/ln 2 > 2^30, i.e. n > about 8.4·10^16; the enclosure is then infinite, never narrows, and step 7
panics with "internal error ... (a bug)". Above about 1.3·10^18 the f64 precision estimate also
saturates its `as u32` cast. Such n are far beyond any feasible run (the linear cost gives about 4·10^7 s
at 8·10^16), but §2.2 ("Exact for every n") and §2.5 ("terminates for every n") must state the
domain. Required: an explicit up-front check (for example `n <= 10^16`, or log2 of the k = 1 term below
`exp_max() - 64`) with a documented `# Panics` naming the reason, instead of the "internal error"
path. Do not widen the global exponent range (it is process-wide MPFR state shared with other crates
and threads).

### m2. Rolling rows allocate k + 1 entries even when the band is narrow
§3.3 bounds the work by the band width w = min(k, n - k + 1) but keeps a row of k + 1 entries
(`vec![Integer::zero(); k as usize + 1]`). For k near n the work is O(n·w) and the memory is O(k):
stirling2(10^8, 10^8 - 1) (a C(n, 2)-sized value, O(n) work) would allocate 3.2 GB of zeros, and J1b's
planned memory check `(k + 1)·(B/8 + 32) <= TABLE_BYTES` would refuse it. Recommended: an offset buffer
of w + 1 entries indexed by j - jmin (the band start rises by one per row once it is above 1). At least
say in §7 that the memory term is k + 1 entries so J1b models it correctly.

### m3. The REPL half of S10 has no owner
§4.2 says "J1b moves the REPL to the Integer versions" and §7 lists it as "J1b's". J1b's design
(`J1b-repl-values-and-limits.md`) never mentions `falling_factorial_integer` /
`rising_factorial_integer` (it only re-measures `falling_factorial(4294967295, ...)`), and J1a
(`J1a-repl-parser-and-small.md` §3) only moves the `pochhammer` name. Required: in the HANDOFF update
(§8.1 step 11) keep "REPL falling_factorial / rising_factorial still take u32 n" as an open item and
report the gap to the orchestrator, rather than recording it as moved to J1b.

### m4. `partition_count_wrapper` is circular
After the change `partition_count` calls `number_of_partitions`, so comparing the two for n <= 300
checks only the conversion. Compare `partition_count(n)` with a test-local copy of HEAD's usize DP
(`partitions.rs:1261-1276`) for n <= 416 (64-bit) instead; that is independent and still pins the old
values.

### m5. The u32 fixes of catalan and schroder_large are untested
§1.1 accepts "checked by inspection". Factor the Schroder multipliers into a private
`fn schroder_step_factors(i: u64) -> (u64, u64, u64)` (3(2i-1), i - 2, i + 1) and unit-test i =
715827884 -> 4294967301 and i = 2147483649 -> 12884901891 (the HEAD expressions give 5 and 3), so the
fix is pinned by a test that the HEAD arithmetic fails.

### m6. rug::Integer -> Integer through a decimal string
num-bigint's base-10 `from_str` is quadratic; §2.4 step 6 measures 20 ms at 370 kbits, so it grows to
seconds at a few Mbits. Use the byte route (`z.to_digits::<u8>(Order::Lsf)` and
`BigInt::from_bytes_le(sign, &bytes)`), the inverse of `rustmath-reals/src/mpfr.rs:368`. Linear and no
new dependency.

### m7. Nits
- §8.1 step 1: `Cargo.lock` also changes (rustmath-combinatorics gains a `rug` entry); list it.
- §1.6 `partition_count` doc: "p(1000) > 2^64, so no target can hold it" should say "no usize of 64
  bits or fewer".
- I3 adds a private `product_tree` over BigUint in rustmath-integers and C1 adds another over Integer.
  Consider making one public in rustmath-integers and consuming it (CLAUDE.md: consume existing
  numeric crates). Not required.
- `TupleIterator` has an inherent `count(&self)` that `Iterator::count(self)` shadows for a value
  receiver (`TupleIterator::new(2, 64).count()` enumerates 2^64 tuples). Worth a line in the doc of
  the fix in B1.

## Checks that the design passes

- Coverage of S2 (the five named sites), S3, S4, S10 (library) and the J1b list: complete apart from B1.
- No facade introduced: `number_of_partitions` returns only a value proved by the enclosure;
  `partition_count`, `stars_and_bars`, `count_partitions_with_max_parts` panic with documented
  messages instead of wrapping or returning 0; `size_hint` returns None instead of a wrong bound.
- No bounded search decides anything (Decided/Unresolved does not apply; the retry cap is a bug guard).
- Tests use gp/GAP values (re-run above); the overflow tests fail on HEAD (debug panic or wrong value);
  the new-API tests do not compile on HEAD.
- Plan order is implementable: Cargo.toml, factorials.rs, partition_number.rs, lib.rs, then the
  sibling files, tests, trackers. The acceptance commands cover the crate, the REPL and the Partition
  users, plus `cargo check --workspace --tests`.
